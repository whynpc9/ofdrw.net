# 《能力路线图开发计划》评审意见

评审日期：2026-09-29。评审对象：[capability-roadmap-development-plan.md](capability-roadmap-development-plan.md)（计划基线 2026-09-28，当时为未提交文件）。评审方式：逐条核对计划对本仓库源码的论断、抽查其引用的上游 ofdrw 源码（固定提交 `5fe9c427`）、与 [能力路线图](capability-roadmap.md) 及 [ticket 索引](../.scratch/capability-roadmap/issues/README.md) 做交叉一致性检查。本评审只改文档，未运行构建、转换或 Preview，不涉及功能/视觉验收结论。

## 总体结论

计划整体质量高，可以按批次开工。22 张票全部有落地方案与验收挂钩；上游基线固定到提交且明确"不把上游 API 名称当作 .NET 已实现"；§1.1 对 .NET 现状的 6 项差异论断经源码核实全部成立；签名/加密分层表述（不提升 `FullyValid`、不改核心能力标志、不宣称互认）与路线图一致并落实到每张票。以下问题建议在首批次（01/02/03）开工前修订，多为一致性与范围界定，不涉及推倒重来。

## 一、源码核实结果

对计划 §1.1、§2、§4 中可验证的 20 项论断逐条核对，**全部成立**，其中 4 处措辞建议更精确：

1. **BuildFonts 的归属。** §1.1 字体行写「`OfdResourceCatalog` 按内容哈希命名载荷，`BuildFonts` 登记字体」，易被读成两者同属一个类型。实际 `BuildFonts` 在 `src/Ofdrw.Net.Packaging/OfdPackageWriter.cs:194`，`OfdResourceCatalog`（`OfdResourceCatalog.cs:13`）只负责按内容哈希命名载荷（`:71`、`:81`）。
2. **BuiltIn 表格只有水平合并。** §1.1 表格行写 BuiltIn 已有「合并列」，属实，但更准确的现状是：仅映射 `GridSpan`（`DocxModelReader.cs:380`、`BuiltInOfdRenderer.cs:187-190`），**没有 vMerge/RowSpan**。这对 16 票有实质影响，见问题 2。
3. **PdfPig 的用途略宽于「文本提取」。** §1.1 PDF→OFD 行写「PdfPig 用于文本提取」；实际还用于页数与页面尺寸（`PdfToOfdConverter.cs:90-91`、`:117-118`、`:191`）。不影响「仅凭现有文字抽取不足以承诺矢量模式」的结论。
4. **共用基础多为 internal。** §2 第 6 点列的 `OfdPackagePruner`、`OfdResourceCatalog`、`OfdPackagePath` 均为 `internal`（`OfdPackagePruner.cs:13`、`OfdResourceCatalog.cs:13`、`OfdPackagePath.cs:8`）。作为内部共用基础没有问题，但 §2.1 审查公开契约时不应把它们当公开扩展点；若某票想让调用方复用路径规范化或资源目录，需要单独的公开化决策。

上游抽查（固定提交原始文件）：

- `OFDSigner.toBeDigestFileList()` 确认：继续签模式只跳过 `Signatures.xml`，保护文件过滤器由调用方提供，并未排除约定 `Annots`/`Signs` 载荷 —— 计划第 23 行准确。
- `SignCleaner.clean()` 确认遍历 `ofd.getDocBodies()` 全部文档 —— §1.1 签名行准确。
- `layout/edit/Attachment` 确认只是 `CT_Attachment` 构造器，无包级删除实现 —— 第 23 行准确。
- 计划**未提及**的一个上游事实：`OFDSigner` 类注释明示「签章和验证操作均针对于 OFD 文档中的第一个文档」。见问题 6。

基线核对：`ae28394` 存在且描述相符（合入能力票文档的 merge 提交）。工作区未提交改动除计划第 7 行所列 5 项外，实际还有 `docs/capability-roadmap.md`（内容仅为回链本计划，无实质影响）——见问题 7。

## 二、建议开工前修订的问题

1. **建议开工顺序在计划与路线图之间不一致。** 路线图 §8 与 ticket 索引均把 11/12（P2 无厂商密码上限）排在第 4 步、06/09（保真与检索）排在第 5 步；计划 §3 却把批次 E（06–10）排在批次 F（11–14）之前，静默调换了优先级。计划第 3 行声明「需求边界以 issue 票和能力路线图为准」，两处顺序应当统一；若有意调换（例如从库使用者视角保真优先于可选密码包），请在 §3 显式说明理由，避免领票人无所适从。

2. **16 票未界定纵向合并单元格（vMerge）策略。** 现状只支持水平合并（见核实结果 2），而 DOCX 表格常见 vMerge。§4 16 行只定义了「整行不可拆、过高行明确失败或受控拆分」，未提纵向合并。公开 `Table/Row/Cell` 的 `Cell` 模型若首版不支持 `RowSpan`，应在契约审查点（§2.1 第一行）和 16 票方案中写明失败或降级行为，防止含纵向合并的输入静默出错。

3. **§2.1 公开契约审查表漏掉 22（骑缝外观）。** 表中 5 行覆盖 20 张票，15 是发布闸门可以豁免，但 22 不在任何票组。22 虽复用 06 的定位结果，其「页面外观写入」契约（图像对象类型、层序、旋转页/不同页尺寸的失败行为）仍应列入审查表，哪怕并入 03/06/07/09/10 行或单列一行。

4. **20 的批次归属不清。** 20 同时依赖 01（批次 B）和 04（批次 D），但 §3 只在 B 行列出「01 + 04 → 20」，D 行未提 20；M1 出口说「16/17/18/20 不启动」，M3 出口却没说 04 完成后 20 何时可启动。建议在 D 行或 M3 补一句「04 完成并通过 M3 后 20 可启动」，否则 20 的实际最早开工点要靠读者自行推断。

5. **Layout 测试落点建议默认新建测试项目。** §5.1 建议「01/16/17/20 放 `tests/Ofdrw.Net.Core.Tests` 中的 Layout 相关用例或新增独立 Layout 测试项目」。现有惯例是一个 src 项目对应一个 tests 项目；让 Core.Tests 引用 Layout 会颠倒这一对应关系，且 §5.1 自身要求「新增测试项目须进入 sln 和 CI」。建议直接默认新建 `tests/Ofdrw.Net.Layout.Tests`，去掉「放 Core.Tests」的选项。

6. **10/13 的风险分析漏了上游签名的单文档限定。** 上游 `OFDSigner` 只签第一个文档（类注释明示），因此「多 DocBody + 继续签」的引用边界在 .NET 侧是新设计：10 引入文档集合后，13 的「显式保护范围」需要按文档界定排除 `Annots`/`Signs` 的目录边界。建议在 §5.3 或 §4 的 13 行补一句提示，防止实施时把上游单文档语义误当成可照搬的多文档语义。

7. **§1 基线段落遗漏一处未提交改动。** 第 7 行列举的工作区改动少了 `docs/capability-roadmap.md`（改动内容仅为回链本计划，无实质影响），补一句即可保持基线陈述的完整性。

## 三、较小建议

- **§5.3 的字体测量风险可以更具体。** `BuiltInOfdRenderer.Advance` 用 PdfSharpCore `XGraphics.CreateMeasureContext` + `XFont` 测量，且 CJK 字形按 1 em 近似（`BuiltInOfdRenderer.cs:344-362`）。抽取共享测量核心时这个近似会显性化，建议把「全宽假设是否保留、可配置还是可替换」列入 §2.1 第一行的审查要点。
- **M4 出口范围未列举票号。** 「其他 P1 票逐项关闭」未说清包含哪些票（06/07/08/09/10/18/19/20/21 中哪些必须、哪些可延后）。建议列明，并与路线图 §8 第 6 步「其余按调用方需求抽」对齐，避免里程碑口径争议。
- **P2-06（证书加密）无票一事建议显性说明。** 路线图有意不为 P2-06 建票，ticket 索引也注明了；但计划 §3/§4 只字未提，读者可能误以为漏票。在 §3 批次 F 或 §4 末尾补一句「P2-06 不在本计划范围」即可。
- **02 的导出实现路径建议在设计评审点中明确。** `OfdToSvgConverter` 当前是单页自包含 SVG（`OfdToSvgConverter.cs:21`）；多页导出的栅格化究竟走 OFD→PDF→位图还是逐页 SVG→位图、ppm 到像素的换算在哪一层发生，建议列入 §2.1 第二行的审查要点。
- **05 可补充字体字节的单一事实来源。** 当前嵌入字节来自 PDF 栈的 `PdfFontRegistry.GetOriginalFont`（`BuiltInOfdRenderer.cs:296-305`）。子集化管线应以它为字体字节的唯一入口，避免 Layout 与 PDF 转换器各持一份字体来源导致子集结果不一致。
