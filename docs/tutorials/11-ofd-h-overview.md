# 11 OFD-H 是什么

上一课：[数字签名结构](10-signatures.md) · 下一课：[OFD-H 包轮廓](12-ofd-h-package-profile.md)

## 这一课结束时

能把 `DocType="OFD-H"` 从“本仓库的默认字符串”还原成一份 **电子病历版式文档技术要求** 的行业轮廓，并知道它和 GB/T 33190、GB/T 42133 的关系。

## 材料从哪来

补充课依据一份 **征求意见稿** PDF（文题《电子病历版式文档技术要求》，英文题 Technical specification for OFD used in Medical record，封面 ICS L67 / CCS 35.240.99，页眉仍为 `GB/T XXXXX—202X`）。文稿标明由国家卫生健康委员会提出、国家密码管理局归口，起草单位包括国家卫生健康委医院管理研究所、中国电子技术标准化研究院及数家医院。PDF 元数据创建于 2025-09-29。

这 **不是** 已发布的国家标准编号。条款可能在后续征求意见中改动。教程只归纳与第 1–10 课的差异，不转录标准正文、表和图。正式合规以当时有效文本为准。

## 它在标准族里的位置

OFD-H 不另起一套图元语言。稿中写明：承载格式固定为 OFD，数据组织符合 GB/T 33190 与档案应用指南 GB/T 42133。可以把它看成：

```text
GB/T 33190     版式容器 + 页面图元（第 1–10 课）
GB/T 42133     档案向的加工与长期保存
OFD-H 征求意见稿   医疗场景下的用法轮廓：单文档、DocType、资源、签章、机读、阅读器行为
```

引用文件还指向日期时间、XML、电子印章、SM2 语法、密码应用标识等。密码应用另见参考文献中的 GM/T 0099。源项目 `ofdrw-archive` 对应 42133；`ofdrw-crypto` 对应 0099。本仓库两者都未做成完整实现（见 [功能对照](../feature-parity.md)）。

## 要解决的问题

引言把电子病历定位成可脱离原业务库仍保持原始性、真实性、长期可读的 **文件**，用来在异构系统之间交付，而不是再造一套中心库。适用对象包括：

- 诊疗活动中形成的电子记录（病历、医嘱、处方、报告、知情同意、护理记录等）
- 需数字化的纸质或设备输出
- 音视频、检查影像
- 外院或患者提交、经审核后纳入的材料

应用框架的要点是 **少改现有 HIS / EMR / NIS / LIS / PACS**：业务系统可以自己生成 OFD，也可以把数据交给机构内归集系统 **代理生成并委托签署**；院际、医联体交换以这份文件（或脱敏后的文件）为单元。

这与本仓库当前角色一致：UniDmrCore 一类业务系统调用转换器产出 `.ofd`，并不在每个业务模块里实现版式引擎。

## 生成时稿中点名的质量门槛

生成与转换应同时做到：内容完整、格式为 OFD-H、签名有效、结构可机读、版本可追溯、安全可控。纸质材料按档案数字化做成 **双层** 版式（图像 + 可检索文字，见 [第 13 课](13-ofd-h-medical-content.md)）。外院文件先审真实性再按是否已符合本轮廓分别采信、扫描或转换。

交换侧常见约定：一般按 **患者** 封装一份文件，内可含一次或多次诊疗；可只给版面，也可给带结构化数据的版面；要有权限控制；交换过程可用注释记入文件。检索应能定位关键内容、版本和交换记录。

## 和前 10 课怎么接

| 已学会的 | OFD-H 额外钉死的 |
| --- | --- |
| ZIP + `OFD.xml` + `Doc_N` | 只用单文档 `Doc_0` |
| `DocType` 可为 `OFD` / `OFD-A` | 病历文件根节点必须是 `OFD-H` |
| 命名空间常为 `…/2016` | 本稿写的是 `http://www.ofdspec.org`（无 `/2016`） |
| 签章可选 | 已生效文件至少一份签名 |
| 字体、图片按需嵌入 | 显示打印所需字型/图像原则上都在包内 |

本仓库 `OfdConstants.DefaultDocType = "OFD-H"` 与 `Namespace = "http://www.ofdspec.org"` 对齐的是 **这篇医疗轮廓的默认值**，不是 GB/T 33190 正文的取值。给通用阅读器或 ofdrw 示例互认时，仍可能需要改回 `OFD` + `/2016`。

## 动手

打开任意本仓库生成的 OFD：

```bash
unzip -p hello.ofd OFD.xml | head -n 20
```

确认根上 `DocType` 和 `xmlns:ofd`。再对照 [第 3 课](03-ofd-xml.md) 决定这次产出的是病历轮廓还是通用 OFD。

## 常见坑

- **把征求意见稿当成已发布 GB 号**。页眉的 `XXXX` 尚未分配。
- **认为 OFD-H 换了一套 TextObject**。图元仍是第 6–8 课那些对象；变的是包约束、资源和签章策略。
- **业务库里的病历 JSON 直接当 OFD-H**。轮廓要求交付物是可脱离原系统的版式文件，结构化数据用标引或附件挂上（第 13 课）。
