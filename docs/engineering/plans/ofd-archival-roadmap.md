## 1. 目标与决策状态

通用 SDK 继续提供 OFD 模型、生成、转换、编辑和呈现；OFD-A 归档能力由调用方显式选用，复用基础能力并承担条款评估、处理决策、证据和交付责任。

已经确定的方向：

- 通用生成和 DOCX/PDF 转换默认 OFD；OFD-H 以后在专门 package 中处理。
- 默认 DocType 修正独立交付，不等待 OFD-A，也不连带修改命名空间。
- 已声明 OFD-A 不等于已验证符合 OFD-A；仅修改标签不能成为归档转换。
- 继续使用现有 105 项条款/附录账本和 AR/AC/APF 规则身份，不另造一套覆盖编号。

本计划采用的实施方案：新增可选归档包，**暂名 `Ofdrw.Net.Archival`**；先发布只读评估，再按证据充分程度开放受限转换。包名、公开 API 和首版支持的字体/对象清单在 A1 的设计提交中定稿，本文中的报告字段是语义要求，不是已存在或已冻结的 API。

本计划编写后的执行指示为“在 local 环境直接完成 D0，然后整体提交推送”。已据此复用验证代码，直接快进集成 main，并将计划和验收摘要一并推送，不另建 PR。此后依据上游对照修订了后续实施与验收要求；本版再依据 #145 复核，补充只读检查基线和各工作包的具体边界。两次修订都不启动 A1–A5、D1、H0、Issue 拆分或 NuGet 发布，也没有修改生产代码或测试。

### 本次修订的实测基线

#145 只记录了 CLI `preflight`（APF）在一份 Native DOCX 产物上的结果，没有记录 17 项 AR/AC 在自有产物上的结果。本次在 `792f0c27` 干净工作区补测，用于界定 A1 的实际工作量；**这是现有只读检查的基线观察，不是新实现的验收，也不涉及页面渲染或视觉验收**。

环境：Linux 5.15（WSL2）x86_64、.NET SDK 10.0.401；宿主仅有一份 Noto Sans CJK SC Regular。输入为 `generated-layout.docx`（SHA-256 `17bea68d…d7bb6`），用 CLI 以 built-in 引擎分别按显式 `native` 和默认模式转换，再把 native 产物的根标签改为 OFD-A 得到 `label-only.ofd`（其余条目字节不变）。

| 检查 | native / default（DocType=OFD） | label-only（仅改根标签） |
| --- | --- | --- |
| APF-001 | Pass | Pass |
| APF-002、003、005、006 | Unknown：`UnsupportedResourceScope`，定位 `Doc_0/Document.xml` | 相同 |
| APF-004 | Unknown：`UnrecognizedControlOrEncryptionScope`，同一位置 | 相同 |
| CLI `preflight` 退出码 | 3 | 3 |
| AR-001、AR-002 | Pass（声明不存在） | Pass |
| AC-001 | Fail `NonArchivalDocType` | Pass |
| AC-002、008、011 | Pass | Pass |
| AC-003–007、009、012 | NotApplicable（完整作用域内无适用对象） | 相同 |
| AC-010、013、014、015 | Unknown（仅发现违规的子集） | 相同 |
| `StandardOutcome` | Fail | Unknown |

由此得到三点，均已对照代码：

1. **APF 层的五项 Unknown 只来自一个原因。** `ArchivalPreflightChecker.ReadXml` 在受检 XML 含 `Extensions`/`CustomTags`/`Annotations`/`CompositeGraphicUnits` 时记 `UnsupportedResourceScope`，`Uncertain` 随即把规则 2、3、5、6（要求未加密时连同 4）标为 Unknown。Native DOCX 的 `Document.xml` 总带 `CustomTags` 声明，因此这五项在自有 Native 产物上恒为 Unknown，与字体和内容无关。
2. **AR/AC 层没有被 CustomTags 阻塞。** `ArchivalStructuralCoverage` 把纯文本的 `Document/CustomTags` 声明视为已识别结构；13 项已可判定，其余 4 项是按设计在缺少来源证据时保持 Unknown 的子集。A1b 的改动点因此集中在 APF 层的作用域判断，不需要重写 AC 规则。
3. **#145 的 `FontPayloadNotDeclared` 取决于宿主字体配置。** 本机三个字体资源（ID 62–64，含 `Noto Sans CJK SC|bold`）都指向同一份内嵌字体文件，粗体为描边模拟，APF-003 因作用域为 Unknown 而非 Fail；#145 所在宿主的同名资源没有 FontFile。两次观察都成立，差异来自生成端的名称字体策略（见 A1c）。

同一组产物还用于观察编辑入口：对 `label-only.ofd` 执行 CLI `delete-pages` 得到的输出仍声明 OFD-A；以它为第一个输入、普通 OFD 为第二个输入执行 `merge`，输出同样声明 OFD-A（见 A2）。

产物、检查输出和哈希清单在本地已忽略的 `artifacts/ofd-a-baseline-20261117/`（`sha256.txt` 的 SHA-256 为 `bf669306…f09806`），未上传，也不是 GitHub 附件。结论仅限该样例、该宿主字体配置和上述两种模式；未在 macOS/Windows 复测，未覆盖 DualLayer、PDF 导入和 Layout 直接生成。

### 上游对照的采用边界

依据[上游 DocType 与 OFD-A 对照](../upstream-doctype-comparison-20261117.md)，固定 Java 上游提交为 `026a53419eeae2a5c0ff5dc467f8b6db19a93d16`。采用其普通生成默认 OFD、基础模型保存声明、独立归档模块和规则/处理器分离的结构；不将其 README 的能力描述或规则数量作为本库符合性判据。

上游默认实际注册 23 条检查规则和 23 个处理器，与 README 部分数量描述不同；这些注册项与本库 105 项条款账本不是同一计数单位。上游转换器没有最终字节后检，静态调用链还暴露源容器缓存未刷新及引用遍历遗漏的风险。本次未运行 Java 转换复现，相关结论与固定源码引用保留在对照文档中；本计划将其转化为本库独立行为的验收要求，不将静态推断写成已执行的上游测试。

后续借鉴具体规则或处理器时，先映射到既有条款 ID，再核对实际实现、适用范围和独立预期。尤其不能以“处理器已注册”“setter 已调用”“未返回违规”分别替代处理完成、最终字节正确和完整归档符合性。

## 3. 现有模块采用什么行为

| 模块/操作 | 后续约定 | 实现责任 |
| --- | --- | --- |
| Core、Layout、OfdPackageWriter；从零生成/排版/绘图 | 新文档默认 OFD；基础模型继续表达图层、附件、动作、签名等能力 | 基础包 |
| DOCX 默认/Native/DualLayer、PDF/图片导入、纯文本转换 | 普通转换输出 OFD；生成方式不代表归档等级 | 现有 Converter / Layout |
| OfdReader、提取、OFD → PDF/PNG/SVG | OFD 与 OFD-A 共用基础路径，保留原声明；缺失 DocType 的通用回退不掩盖归档检查对原始 XML 的检查 | Reader / 导出器 |
| 字体嵌入、子集、媒体解码、资源解析 | 可复用的通用技术能力；不内置机构归档政策 | 现有基础能力所属包 |
| 字形必须保留范围、字体豁免、附件处置、签名长期证据 | 判断适用条款及是否具备交付证据 | 归档层 |
| 已发布 Packaging.Preflight 下 Archival* | 保留类型、程序集位置和行为兼容；由新包组合使用 | Packaging + 归档适配层 |
| 用户可见的编辑/拆合/批注入口 | 拒绝直接修改 OFD-A 原件并提示；需要复用时显式创建普通 OFD 派生副本 | A2：编辑/CLI 入口与归档派生策略 |

OFD-A 的读入、导出与验证不应被禁止。编辑保护针对改变内容的操作，不能用“禁止编辑”阻断只读检查或格式导出。保护也不以整部标准验证成功为前提：遇到声明为 OFD-A 的原件，先保护原件，再分别报告声明是否可信。

派生副本默认 OFD，记录源文件身份、声明和操作，明确不继承归档结论或原签名有效性。签名输入在未建立专门派生策略前拒绝；禁止无声删除签名，或把已变更字节当作仍有有效签名。是否调整低层通用 editor 的公开行为，先做兼容性评审；不靠给所有属性 setter 加限制实现读端要求。第三方阅读器的编辑禁止及提示另行实测，不能由 SDK 自行证明。

## 4. 包依赖与报告契约

依赖方向：`Archival → Packaging → Core`。只有具体消费者确需 Reader、字体解析等基础能力时才增加直接依赖，并记录原因；避免反向引用与循环。普通 Converter 元包不默认引入 Archival，首版 Archival 不强制携带 DOCX/PDF 转换器或阅读器 GUI。

第一版复用已发布的 Preflight API，不搬 public 类型、不复制检查器。需要扩展通用资源遍历或字体字节验证时，在实际所属模块增加窄接口；保留旧 APF 行为，新增能力通过明确入口或版本化策略启用，避免普通 `preflight` 结果无说明地改变。已有项目使用 netstandard2.0/netstandard2.1；新包需明确兼容目标及依赖，不为了首批验证顺手升级整仓 TFM。

包消费验收检查实际传递依赖：普通 Converter 消费者不引入 Archival，归档消费者显式引用它。上游 Archive 直接依赖 Reader/Crypto 不构成本库首版引入这些依赖的理由；解密能力仍随 A5 的具体范围设计。

报告至少分开表达以下事实：

| 维度 | 必须记录 | 不允许的推导 |
| --- | --- | --- |
| 声明 | 原始 DocType、是否缺失/异常、源字节身份 | Reader 回退值证明原始声明存在 |
| 输入支持 | 选定 profile、支持/超范围/未知及原因 | 超出首版能力即违反国标 |
| 单条款 | 条款、规则、适用性、Pass/Fail/Unknown/NotApplicable、路径/对象/证据 | 未找到对象即自动 Pass |
| 文档整体 | 已覆盖范围、缺口、适用标准版本 | 所有已实现检查 Pass 即整部标准 Pass |
| 软件要求 | 第 7 章写入端/阅读端证据、构建和检查范围 | 单文件通过证明阅读器行为符合 |
| 外部认可 | 机构政策、PKI/独立核准材料及认证状态 | 自填材料、哈希正确即机构已认可 |
| 执行状态 | 完成/取消/预算耗尽/错误；检查器与 profile 版本 | 不完整运行出具“可交付”结论 |

首版可以声明“某有界规则 Pass”，整体 `StandardOutcome` 仍沿用 Fail/Unknown，不新增笼统 `IsCompliant=true`。超范围与规则违规分开：发现确定违规仍保留 Fail，但不能仅因不支持附件或签名就伪造条款失败。

普通 OFD 的声明不满足 OFD-A 标识条款，只表示它不是所要求的归档子集，不能据此称其为非法普通 OFD。基础模型允许显式保存 OFD-A 等声明，也不因此触发自动归档处理或颁发归档结论。

### D1：生成端字体自包含选项（已决定立项）

A1c 只能判断字体是否自包含，不能让产物变得自包含。按现行[转换契约](../../content/reference/conversion-contracts.md)，Native DOCX 在两种情况下**按设计**只声明字体名称、不写 FontFile：宋体、黑体、等线、楷体、仿宋、微软雅黑等系统中文族始终如此；`Noto Sans CJK*` 未从字体目录加载到真实字节时也是如此（`DocxFontCatalog.ShouldEmbed`）。这是为阅读器本机字体兼容保留的行为，#145 观察到的 `FontPayloadNotDeclared` 即出自此路径。结果是：使用最常见中文字体名的 DOCX 目前无法经 Native 模式产生字体自包含的 OFD，无论宿主是否装有该字体。

候选内容是在基础转换包增加显式选用的策略：所有已用字体必须取得真实字节并嵌入，否则转换失败并指出字体族和原因。默认行为不变，名称字体兼容路径保留。开工前需要先有字体许可与嵌入权限（含字体自身的嵌入许可位）的处理依据；不能以“宿主能解析到字节”代替授权。涉及字体与排版，须按视觉验收规则检查显式 native 和默认模式的实际页面。

D1 不依赖归档包，可独立于 A1 交付；A1 不等待 D1。A3 若要接纳使用系统中文族的 DOCX 来源，则以 D1 或等价的受控字体输入为前提。维护者已于 2026-11-17 决定立项。嵌入权限的处理依据定为：读取字体自身的嵌入许可位，标明限制嵌入的字体拒绝嵌入并报告；许可位允许嵌入不等于取得授权，授权仍由调用方负责，诊断中如实说明。不以其他字体族的替代字节冒充所声明的字体族。

### H0：OFD-H 独立包（未立项）

方向已定为独立包，名称、API 和专用标准范围均未设计。立项前需要：专用规范的准确文本和版本、真实消费者与样例、独立的验证 profile。立项后不得把专用默认值或专用校验带回通用包。

有一处遗留需要在 H0 或 A1b 之前明确归属：通用 Native DOCX 输出的来源标签仍借用 EMR 通道，实际写出 `TypeID="EMR"`、`NameSpace="urn:ofdrw-net:custom-tags:emr"` 和 `EMRTags` 载荷。D0 只改了根 DocType，没有触及这一通道。A1b 会把当前结构登记为已知 schema，之后若迁移到中性通道，检查端须同时识别新旧两种结构；维护者已于 2026-11-17 决定**另立中性通道**（工作包 D2）：新生成的文档经中性通道写出来源标签，声明的命名空间与载荷根一致；历史 EMR 通道的输入读取时保持原键值语义，原样保存时不被强制改写；EMR 通道今后归 OFD-H 专用包。A1b 同时登记新旧两种结构。

## 7. A1：先让自有产物得到准确评估

§2 的实测基线给出了 A1 的起点。A1 完成后可观察的变化限于两处：已知 CustomTags 不再使 APF 层五项规则无差别 Unknown；字体从“声明了非空文件”提升到“字节可解析且覆盖已用字形”。AC-010、013、014、015 在 A1 结束后**仍为 Unknown**，这是缺少来源证据时的正确结果，不是 A1 未完成；AC-001 对普通 OFD 仍为 Fail，属于声明维度的事实。

### A1a：明确第一批输入与只读入口

首批选择本库生成的单 DocBody、未签名、未加密、无附件、无 Versions 历史文档；覆盖简单 Layout 与受控字体的 Native DOCX，保留其来源 CustomTags。不以“由本库生成”作为信任证明，每项仍检查实际包内容。

设计提交同时交付首批 profile 的**条款适用性矩阵**，对应 #145 “明确强制/推荐/条件条款及外部证据需求”一项。105 项账本逐项标注：规范强度（应/不应、宜、可、条件适用）；在首批 profile 下是可由包内容判定、经完整作用域证明后不适用、需要外部证据，还是超出范围；以及引用标准的适用版本是否已固定。现有 `ArchivalClauseDefinition` 只有条款、条件、剩余证据、规则和处理器，没有规范强度字段，账本正文仅以“优先”等措辞体现。强度须对照标准的渲染页面核对（公开副本的可提取文本有乱码），不凭账本措辞推断。“宜”和“可”类条款未满足时不得计为 Fail。若为目录增加字段，属于对已发布类型的增量修改，并提升账本修订号。

在设计提交列出接纳的页面对象、资源类型、标签 schema 和字体格式。首批不处理动作、批注、扩展或未知图形语义；发现这些内容时报告超范围/Unknown，保留能独立确定的条款结果，不通过丢弃内容扩大支持范围。DualLayer 与 PDF 导入仍是普通 OFD 能力，不自动计入首批归档 profile。

首版公开能力只读输入、返回分维度报告及缺口，不生成 OFD-A、不执行删除或修复。报告绑定稳定的输入快照及哈希，记录原始 XML 声明；检测过程遵守现有 ZIP/XML 路径、重复条目、大小、遍历预算和取消约束。

新增测试应证明正常样例、缺资源、未知作用域、超范围输入、预算耗尽/取消分别落入正确结果。缺失 DocType 必须由原始 XML 检出；不能通过 Reader 的 OFD 默认回退漏报。

原始声明检查直接复用 `ArchivalCoverageService` 的 AC-001：它已区分缺失、非归档声明及外来同名属性歧义。A1 的工作是将既有结果正确映射到新报告，不再另建等价规则。复用既有单元用例；仅为新的公共报告入口补集成断言，覆盖普通 OFD、显式 OFD-A、缺失声明和歧义声明，并确认读入不会改写输入字节。

### A1b：保留并理解来源标签

代码入口：

- `src/Ofdrw.Net.Converter.Docx/Internal/BuiltIn/BuiltInOfdRenderer.cs` 写入 `source-text-origin=DOCX/OpenXML` 等 Native 来源信息。
- `src/Ofdrw.Net.Packaging/OfdPackageWriter.cs` 的 `BuildCustomTags` 使用当前 EMR 标签载荷结构。
- `src/Ofdrw.Net.Reader/Readers/OfdReader.cs` 保留已知及不透明 CustomTags 来源。
- `src/Ofdrw.Net.Packaging/Preflight/ArchivalPreflightChecker.cs` 当前对 CustomTags 等作用域返回不确定。

当前实际写出的结构（§2 基线产物）只有三级，且载荷内没有包路径或对象引用：

1. `Document.xml` 的 `CustomTags` 元素文本 `Tags/CustomTags.xml`，相对 `Document.xml` 解析。
2. 索引内 `CustomTag`（`TypeID="EMR"`、`NameSpace="urn:ofdrw-net:custom-tags:emr"`）的 `FileLoc` 元素文本 `CustomTag_EMR.xml`，相对索引解析。
3. 载荷根为 OFD 命名空间下的 `EMRTags`，子元素 `Tag` 以 `Key`/`Value` 属性携带纯文本值，例如 `source-text-origin=DOCX/OpenXML`。

A1b 的工作量因此小于“通用标签遍历”：改动点是 §2 所述 APF 层的 `UnsupportedResourceScope` 判断，AC 层已接受该声明形态。设计时需要对两处观察作出明确处理，而不是默认放行：索引声明的 `NameSpace` 与载荷根实际所在的命名空间不一致；索引没有 `SchemaLoc`。两者是否符合 GB/T 33190 对自定义标引的要求尚未对照标准核实，核实前按“已知的本库写出形态”登记，不表述为符合标准的标引。既有 `ofdrw-local-preflight/0.1-draft` 修订 1 的结果保持不变，新的作用域判断通过新入口或新的 profile 修订启用。

实现针对明确 schema 的 Document → 标签索引 → 载荷及其已定义引用的遍历；区分包路径引用与纯文本值，不把任意标签值当路径。检查命名空间、目标存在性、包内路径、角色冲突、重复/歧义和预算；对循环引用明确终止。

引用解析使用 XML 字段语义及相应包路径规则，同时覆盖元素文本引用和属性引用；不得以扫描引号内字符串的正则构建资源白名单。用 DocRoot 文本、资源相对路径及已知标签引用验证正文/资源均可到达；未知 schema 保持 Unknown，不凭缺少已知边判定文件无用并删除。

不能删除 `source-text-origin` 来让预检通过，也不能把所有 CustomTags 直接列入白名单。EMR 标签 schema 与根 DocType=OFD-H 是不同层次；首批兼容当前实际写出的标签结构，不在此 PR 搬迁标签格式或开发 OFD-H 专用包。

验收至少包含：已知完整标签、缺失目标、越界目标、未知 schema、同名外来命名空间、混合已知/未知内容与循环/预算。已知分支能够定位结果，未知分支仍 Unknown；原始标签字节和来源语义不因只读检查而变化。

### A1c：字体检查基于实际载荷和使用字形

现有字体解析与子集代码在 `src/Ofdrw.Net.Core/Fonts/`（`OpenTypeFace`、`TrueTypeSubset`、`CffSubset`、`OpenTypeGlyphClosure`）和 Packaging 的 `OfdFontEmbeddingPlan`，均为 internal；Core 通过逐个列名的内部可见性向仓内现有程序集（Packaging、Reader、Layout、Signatures、各 Converter、Graphics.SkiaSharp 及测试）开放。新的归档包不在名单内，不能直接调用。A1a 的设计提交须在两种做法中定一种：在 Core 或 Packaging 增加面向字节验证的窄公共接口，或为归档包增加内部可见性。本计划建议前者，避免归档包绑定到尚未稳定的内部类型；无论哪种，依赖方向仍是 `Archival → Packaging → Core`，不需要引入 Layout 或 Reader。

判断以包内字节为准，不以资源声明为准。基线产物中 `Noto Sans CJK SC|bold`、`…|regular|italic`、`…|regular` 三个字体资源共用同一份 Regular 字体文件，粗体由描边模拟：`FontName` 和样式标志描述的是请求样式，不是物理字体面。首批 profile 的输入必须让每个已用字体族都走嵌入路径，即从字体目录提供真实字节，并且文档不使用始终保留名称字体的系统中文族（见 D1）；不满足时报告为超范围或缺载荷，不调整样例去回避。

复用现有字体解析及子集能力，先选定许可明确、版本和 SHA 固定的字体与受支持格式。验证文本与裁剪文字实际引用的字体、字符/GID 映射、使用字形及必要表；未知字体格式或无法可靠解释的映射保持 Unknown，不以 OS 能找到同名字体代替包内证据。

没有 FontFile 时分别判断：有明确条款依据且满足条件的豁免；已证实不满足要求；证据不足。对 GB/T 33190、字符集和字体豁免的适用版本未核实前，不把 APF 的局部缺载荷策略升格为通用标准判断。许可与允许嵌入的记录独立保留，不能由字形能解析推导授权。

测试包括完整字体、合法子集、缺载荷、损坏载荷、缺实际使用字形、裁剪文字引用、错误 ID/映射及可证明/不可证明的豁免。错误需定位包路径、字体/对象 ID 和原因；允许复用同一 fixture 做有目的的变体，避免重复字体文件。

必须包含“FontFile 存在但字节损坏”和“字体可解析但缺实际使用字形”两类负例，证明能力超出文件存在性检查。按声明所属资源表及 BaseLoc 语义解析字体路径，不统一相对于 ZIP 根寻找所有 FontFile。

## 8. A2：编辑保护与普通 OFD 派生

这是本库明确选择的产品行为；上游普通编辑路径没有提供相同保护。不能以“与上游 API 相同”作为本阶段验收，也不把应用层保护强塞到所有低层模型赋值操作。

**现状（§2 补测）：归档声明会随编辑和合并传播。** `OfdDocumentMerger.CloneOptions`（拆分与合并共用）和 `OfdOwnedEditCandidate` 复制源文档的 `DocType`。实测对声明 OFD-A 的输入执行 `delete-pages`，输出仍声明 OFD-A；`merge` 的输出沿用第一个输入的声明，把普通 OFD 的页面并入后仍标为 OFD-A。内容已改变的输出因此可能带着未经任何检查的归档标识，这正是 #145 要避免的“标签被当作符合性”。在 A2 完成前，这一行为应写入用户文档的已知限制。

同时存在一项需要兼顾的既有契约：读入后原样写出会保留显式声明，D0 的 roundtrip 测试即以 OFD-A 验证属性保存。A2 的设计必须划清“原样保存”与“改变内容的操作”，并在操作入口处理，不在写出器或模型属性上一刀切；这也是兼容性评审的核心问题。

盘点所有改变内容的公共入口，形成矩阵，标明原件是否只读、是否可生成派生副本、输出声明、如何处理签名和来源。已核对到的入口至少包括：

- Layout 编辑：`OfdDocumentEditor`、`OfdDocumentSplitter`、`OfdDocumentMerger`、`OfdDocumentMixer`、`OfdTextReplacer`、`OfdNamedAreaEditor`、`OfdWatermark`、`OfdSignatureCleaner`。
- 其他包：`OfdDocumentPackage.RemoveAttachment` 与物理清理、Signatures 的签名写入、Crypto.Password 的加密写出。后两者分别涉及 6.13 和 6.16，对归档原件追加签名或加密是否允许需单独决定。
- CLI：`replace-text`、`reorder`、`delete-pages`、`crop`、`attachments remove`、`areas fill`、`watermark`、`split`、`mix`、`clean-signatures`、`merge`。

`OfdSignatureCleaner` 与 `clean-signatures` 会移除签名声明和载荷，须按下文“禁止无声删除签名”单独列出处置。多输入操作（`merge`、`mix`）要规定任一输入声明 OFD-A 时的行为，不能只看第一个输入。

保护依据是原始声明，不依赖归档评估结果，因此声明判断应放在基础包：Layout 不应为此引用归档包，否则普通消费者会被动带入归档依赖。入口盘点和“输出不继承归档声明”这一部分不依赖 A1，可先行评审；派生副本的来源记录沿用 A1a 的报告语义。

用户层遇到 OFD-A 时给出明确提示和可选择的派生路径；普通 OFD 编辑保持兼容。

派生使用不同目标文件和稳定源快照，默认 DocType=OFD，记录内容变化和来源哈希；不能覆盖归档原件，不能沿用旧报告或旧签名有效性声明。失败和取消不得留下可被误认作成功的输出。

用公开入口验证 OFD 普通编辑、OFD-A 原件拒绝、显式派生、签名输入拒绝、错误/取消及原件哈希不变。另需覆盖：未改内容的 roundtrip 仍保留显式声明；改变内容的每类入口的输出声明符合矩阵；多输入操作中 OFD-A 输入不在首位时的结果。独立 OFD 阅读器的查看、编辑提示与未处理项报告作为第 7 章单独验收，不以 Preview 打开导出 PDF 代替。

## 9. A3：可审计的受限归档转换

开启条件：A1 已能准确解释所选输入；已有适用条款、处理器、外部证据与未覆盖项清单。**A1 检查通过不自动满足此条件**；简单输入仍可能存在资源、颜色、元数据、软件或政策证据缺口。

流程：稳定源快照 → 只读评估 → 版本化处理计划 → 独立临时候选 → 标记候选 OFD-A → 重开最终字节后检 → 判断交付资格 → 原子提交输出及可关联报告。

处理器结果统一序列化到同一个候选包，关闭写入句柄后，后检必须从该候选 ZIP 重新读取，不复用处理器的内存模型或另一实例的旧缓存。后检完成后不再修改候选字节；报告绑定最终候选哈希，输出提交使用同一份已检字节。复用现有 `ArchivalCopyConverter` 的有限副本/后检边界，不将其两项清理直接包装成完整归档转换。

输入与成功输出必须为不同文件，覆盖源目标同路径及可识别的文件别名。失败或取消不得截断源文件或已有目标，也不得留下能被当作成功交付的文件。输出与报告的提交顺序和失败恢复在实现规格中明确，避免输出更新但旧报告仍被当作当前结果。

计划列出源哈希、profile、处理器版本、条款、对象、保留/修改/移除/拒绝原因和预期信息损失。执行时核对计划与源身份；输入漂移、预算耗尽、取消或后检失败均不发布归档交付件。复用 Permissions/VPreferences 处理，但不能默认其余条款已经满足。

候选文件的 OFD-A 标记只为最终字节检查服务，不可作为“已交付”的信号。适用必需条款或所声明交付范围需要的外部证据缺失时，结果为未达到交付条件。确需保留诊断候选时，置于明确的内部工作目录并标明未获准交付；不出现在成功输出位置。保持现有整体 StandardOutcome 语义，若未来扩大整体判断能力，须单独审查覆盖和兼容性。

验收应覆盖源未变、处理计划可复查、修改前后身份与未改条目哈希、最终字节后检、源漂移、无法处理项、后检失败、取消和输出提交失败。所有会改变外观/语义的操作都有来源到结果的对照。此阶段不接纳签名输入或通用解密，除非对应 A5 工作包已经独立完成。

针对上游对照暴露的边界，增加以下有判别力的集成用例；这些是待实现后的验收项，不是本次修订已通过的测试：

| 用例 | 必须观察的最终结果 |
| --- | --- |
| 处理器只修改内存中的 DocType，尚未持久化 | 候选最终 ZIP 的根属性未正确写出时不得交付；断言从重新解包得到的 XML 读取 |
| DocType 已为 OFD-A，但 DocRoot、正文或资源因引用遍历遗漏而缺失 | 明确失败并定位断链；标签通过不能掩盖结构或内容丢失 |
| 处理器返回成功，但指定修改未实际应用，或另一条适用规则失败 | 后检发现不满足计划或条款，不提交归档成功结果 |
| 最后一步失败/取消，或源目标为同一文件/别名 | 原件与已有目标保持原字节；没有成功交付记录 |
| 后检后候选或报告身份改变 | 不将未经核对的字节作为已检输出发布，报告不会关联到错误文件 |

测试以真实公共转换入口和最小可注入失败边界完成，不为模仿上游缓存结构而引入第二套生产实现。

## 10. A4/A5：按真实需求扩展

| 分组 | 内容 | 开放前必需材料 |
| --- | --- | --- |
| A4 动作与链接 | 外部动作处置、内部链接迁移、移除摘要 | 来源动作清单、目标有效性、正反例及交互验证 |
| A4 批注与扩展 | 冻结/扁平化、保留外观、管理批注分离 | 来源解释、对象归属、文本/逐页视觉及打印证据 |
| A4 页面与资源 | 页面区域、图层/PageBlock、颜色/ICC、裁剪、图像实际格式等 | 每项应/宜属性、真实字节/几何检查、独立呈现比较 |
| A5 文档与版本 | 拆合、来源、Versions 与无关文件处理 | 来源文档身份、完整引用图、保留策略及转换清单 |
| A5 附件 | 保留/转换追加/外部化与摘要，附录 A 按类别开放 | 真实样例、接收政策、内容顺序、信息损失和独立输出验证 |
| A5 加密 | 识别、授权解密、明文证据 | 明确算法与格式范围、密钥处理边界及前后身份 |
| A5 签名 | 有条件保留或去技术化、印章外观及签署信息 | 适用标准、来源签名验证、CA/注册/长期状态和机构接受证据 |

每组拆成可独立验收的小任务，先固定输入/输出和拒绝条件，再实施。没有真实需求与证据的类别继续延期，不以 DOCX 转换能力代表附录 A 全部文字处理或全部附件类别。通用验签、附件物理删除和现有合并 API 仅是组件，不能直接替代归档决策。

以下内容保留要求作为相应工作包的开放条件，不能以最终单条 XML 检查通过代替：

- **多文档**：默认拒绝尚不支持的输入；开放拆分/合并后，核对所有来源文档的页面、文本、资源、顺序和来源映射。不以删除第二个及后续 DocBody 达到“单文档”要求。
- **扩展与批注**：删除声明前，证明需保留的显示/打印外观已冻结或有明确的不适用依据；只有节点不存在不能证明转换正确。缺少来源解释时拒绝相应转换。
- **签名/签章**：处理前验证来源与适用策略，按所选分支保留必要身份、时间、摘要、证书信息和外观。签名目录已删除不代表去技术化完成，也不能沿用原有效性声明。正例之外必须覆盖信息未保留、外观丢失及外部证据不足的拒绝用例。
- **附件**：文件扩展名不单独决定删除；按真实内容和保留政策选择保留、转换追加或外部化，并验证摘要、顺序与信息损失记录。需要保留的内容没有对应结果时不交付。
